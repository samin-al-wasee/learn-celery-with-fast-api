# Cardicheck

A **doctor–patient medical platform** built as a **learning project** for **FastAPI + Celery** — from basic to senior level, focused on what matters in technical interviews.

> **This is not "just" an app. The app is the vehicle. The real deliverable is understanding.** Every feature we build is chosen because it forces us to hit a core learning topic (caching, message queues, async jobs, bidirectional communication, distributed systems). We deliberately write naive versions first, hit the classic pitfalls, then refactor to best practice — and we document the whole journey.

---

## What we're building

1. **Doctor & patient accounts** — signup, login, profile, and basic CRUD (appointments, prescriptions, medical records) against a PostgreSQL database.
2. **Realtime chat** — 1-on-1 doctor/patient messaging (bidirectional communication).
3. **Voice & video calling** — WebRTC-based calls (this is where deep protocol understanding pays off in interviews).
4. **Supporting features unlocked by the learning topics** — e.g. async notifications, email/SMS jobs, cache-heavy read paths, an event bus between services.

## Topics this project exists to teach

| # | Topic | Where it lives in the project |
|---|-------|-------------------------------|
| 1 | Caching | Redis-backed read paths (profiles, chat history, lookups) |
| 2 | Microservices / Distributed systems | Splitting the monolith into services, service-to-service communication, failure handling |
| 3 | Bidirectional communication | WebSockets (chat), RPC-style patterns, event publishing/consuming |
| 4 | Message queues / RabbitMQ | Celery broker, pub/sub events, at-least-once vs exactly-once semantics |
| 5 | Celery | Async jobs, retries, task routing, beat schedules, monitoring |
| 6 | Asynchronous jobs | Anything slow/non-request-critical moved off the HTTP request path |

## Our learning philosophy

- Best practices are learned by **understanding why they exist**, not by memorizing them.
- We walk the **naive path first**, document exactly why it breaks, then upgrade.
- We **deliberately make common mistakes** in a controlled way to see the failure mode with our own eyes.
- Every decision, mistake, and fix is logged so it stays a reference, not just a memory.
- Everything is **interview-focused**: every concept we touch gets a "what would you answer in an interview" section.

## How to run

```powershell
docker compose up -d            # start postgres, redis, rabbitmq
python -m venv .venv            # first time only
.venv\Scripts\Activate.ps1      # activate (PowerShell)
pip install -r requirements.txt # first time only
uvicorn app.main:app --reload   # run the FastAPI API (from project root)
```

Celery (added in M3):
```powershell
celery -A app.worker.celery_app worker --loglevel=info   # run a Celery worker
celery -A app.worker.celery_app beat --loglevel=info     # run the scheduler (when needed)
```

Live docs: `http://localhost:8000/docs` (Swagger UI auto-generated by FastAPI). Health check: `http://localhost:8000/api/v1/health`.
